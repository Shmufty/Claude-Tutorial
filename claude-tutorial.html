01

Projects

A project is persistent context, so you stop re-explaining yourself every session.

Claude starts every conversation knowing nothing about you. It doesn't remember your thesis topic, your coding style or the folder layout of your repo. A project fixes that by attaching standing instructions and reference material to a workspace, so every conversation inside it starts informed. The idea exists in two forms that behave differently, so it's worth separating them.

Two kinds of "project"

claude.ai

Projects in the app

A named workspace in the web/desktop app with:

  • Custom instructions: tone, role, rules ("answer as a reviewer of a MSc thesis in engineering").
  • Knowledge files: PDFs, notes, data you upload once and reuse in every chat.
  • Chat history grouped in one place.
Claude Code

Your repo folder

No special object to create. The project is the directory where you run claude. Claude reads:

  • CLAUDE.md at the root, loaded at every session start.
  • .claude/ with skills, agents, commands and settings.
  • The actual files, which it explores with search tools on demand.

Setting up a Claude Code project, step by step

  1. Open a terminal in your project folder.
  2. Start Claude and run /init. It scans the code and drafts a CLAUDE.md.
  3. Open the draft and cut anything generic. Keep only what Claude can't guess from the code.
  4. Commit CLAUDE.md so teammates (or future you) get the same behavior.
  5. Add rules as you hit problems: each time Claude gets something wrong twice, write a line.
cd my-thesis-code
claude
> /init            # Claude scans the repo and drafts CLAUDE.md

Typical layout:

my-project/
├─ CLAUDE.md              # project memory, always loaded
├─ CLAUDE.local.md        # your private notes, not committed
└─ .claude/
   ├─ skills/             # reusable playbooks
   ├─ agents/             # subagents
   ├─ commands/           # custom slash commands
   └─ settings.json       # permissions, hooks

What a good CLAUDE.md contains

# Project: Soil moisture forecasting (MSc thesis)

## Commands
- Run tests: `pytest -q`
- Train model: `python train.py --config configs/base.yaml`
- Lint/format: `ruff check . && ruff format .`

## Conventions
- Python 3.11, type hints on public functions.
- Data in `data/raw` is read-only. Never edit it; write to `data/processed`.
- Plots: matplotlib, save to `figures/` as PDF.

## Gotchas
- `utils/io.py` caches to disk; delete `.cache/` if results look stale.
- Do not commit anything under `data/`.

Memory layers

LayerWhereUse it for
Organization / user~/.claude/CLAUDE.mdPreferences across all projects (language, style, "ask before deleting").
Project (shared)./CLAUDE.mdTeam conventions, commands, architecture notes.
Project (private)./CLAUDE.local.mdYour local paths, sandbox URLs. Add to .gitignore.

Use /memory to open and edit these files from inside a session, and start a message with # to quickly append a note to memory.

Using app Projects well

  • Upload source material you reference repeatedly: syllabus, style guide, paper PDFs.
  • Write instructions as a role plus rules plus output format, e.g. "You are my thesis advisor. Be critical. Cite the uploaded paper by section."
  • One project per ongoing effort. Mixing unrelated topics makes answers vague.
  • Ask Claude to quote the knowledge file when making claims, so you can verify.
Best practicesKeep CLAUDE.md under roughly 100 to 200 lines. Prefer commands and concrete rules over prose. Review it monthly and delete what's stale.
Common mistakesDumping the whole README into CLAUDE.md. Writing vague rules ("write good code"). Putting secrets or API keys in a file that gets committed.
02

Skills

A skill is a packaged playbook Claude loads only when the task matches.

CLAUDE.md is always in context, so everything in it costs attention on every turn. Skills solve that: a skill is a folder of instructions (and optional scripts or templates) that Claude pulls in only when relevant. Think of CLAUDE.md as the employee handbook and skills as the specific how-to guides you open when the situation arises.

How skills load

Session starts→Claude sees each skill's name + description→Your request matches→Full SKILL.md loads→Supporting files read if needed

This "progressive disclosure" means you can install dozens of skills without bloating the context window. The description is the most important line you write: it decides whether the skill ever triggers.

Anatomy of a skill

.claude/skills/weekly-report/
├─ SKILL.md            # required: frontmatter + instructions
├─ template.md         # optional: output template
└─ scripts/
   └─ summarize.py     # optional: deterministic helper

--- SKILL.md ---
---
name: weekly-report
description: Draft my weekly research update from git history and notes. Use when asked for a weekly report, progress update, or status summary.
---
# Weekly report

1. Run `git log --since="1 week ago" --oneline` to see what changed.
2. Read `notes/this-week.md` if it exists.
3. Group work by theme, not by commit.
4. Fill in `template.md`. Keep it under 150 words.
5. End with one question I should raise with my advisor.

Where skills live

Project skills

.claude/skills/ inside the repo. Shared with anyone who clones it. Best for workflows tied to that codebase.

Personal skills

~/.claude/skills/. Follow you into every project. Best for personal habits (commit style, writing voice).

Plugin skills

Installed with a plugin (see section 06). Namespaced like plugin:skill so names don't clash.

Writing a description that actually triggers

WeakStrong
"Helps with reports.""Draft my weekly research update from git history and notes. Use when asked for a weekly report, progress update, or status summary."
"Code review stuff.""Review a diff for bugs, missing tests and unclear naming. Use after code changes or when the user says 'review'."

Say what it does and when to use it, including phrases you'd actually type.

Skill or slash command? Not the same thing

People often mix these up, because both are Markdown files and both can show up in the / menu. The key difference is who decides when it runs: Claude picks up a skill on its own when your request matches it. A slash command runs only when you type it.

SkillSlash command
Who starts itClaude, automatically, when your request matches the description. You can also type /skill-name.Only you, by typing /name. It never runs on its own.
What it isA folder: SKILL.md plus optional scripts, templates and reference files.Built-in: a control in Claude Code itself (/compact, /model). Custom: one saved prompt in .claude/commands/name.md.
What it changesHow a kind of task gets done.Built-in ones change the session: context, model, tools, permissions.
Context costName and description are always loaded. The full file loads when it triggers.Nothing until you run it.
Pick it whenClaude should apply the procedure whenever it fits, even if you forget to ask.You want a deliberate action at a moment you choose.

The two are getting closer: a custom command is basically a skill that only runs when you call it. To make a skill work that way (for example, a deploy you never want triggered by accident), add disable-model-invocation: true to its frontmatter.

Skills vs. the alternatives

NeedUse
A rule that must always applyCLAUDE.md
A multi-step procedure used sometimesSkill
A saved prompt you trigger by handCustom slash command
Heavy work you want isolated from your chatSubagent
Access to an external systemMCP server

Fast way to create one

Describe the workflow to Claude and ask: "Turn what we just did into a skill called weekly-report in .claude/skills." Then test it in a fresh session. If it doesn't trigger, sharpen the description.

Rule of thumbDoing the same multi-step thing for the third time? Make it a skill. Keep each SKILL.md focused on one job, and move bulky reference text into separate files it can read on demand.
Common mistakesA vague description (never triggers). One giant skill that does five things. Skills that duplicate CLAUDE.md. Installing third-party skills without reading them: they can instruct Claude to run commands.
03

Agents & subagents

Subagents are specialists that work in their own context window and report back a summary.

Claude Code is already an agent: it plans, calls tools (read files, run commands, edit), looks at results and loops until the job is done. A subagent is a second agent that the main one delegates to. It gets a fresh context, its own system prompt and its own tool permissions, does the task, and returns only the conclusion.

You→Main Claude→Subagent (own context)→Summary only→Main Claude

Why they matter

Context hygiene

Searching 40 files for where an error comes from floods your window. A subagent reads them all, and your main chat receives one paragraph.

Specialisation

A reviewer with a strict prompt and read-only tools behaves differently from a general assistant that "wants to help" by editing.

Parallelism

Several subagents can work at once: one per module, one per paper, one per test suite.

Safety

Restrict tools. A researcher that can only Read and Grep cannot modify anything by accident.

Built-in helpers you already have

  • Explore: fast, read-only search across a codebase. Used when Claude must find things before acting.
  • Plan: drafts an implementation approach without changing files.
  • General-purpose: a catch-all for multi-step research and tasks.

You can steer them in plain language: "Use subagents to check each of the four modules for the same bug, in parallel, and summarise the differences."

Create your own

Run /agents for a guided wizard, or write a Markdown file. Project agents go in .claude/agents/, personal ones in ~/.claude/agents/.

.claude/agents/code-reviewer.md

---
name: code-reviewer
description: Reviews diffs for bugs, missing tests and risky patterns. Use proactively after any code change.
tools: Read, Grep, Glob, Bash
model: sonnet
---
You are a strict senior reviewer.
- Run `git diff` to see what changed.
- Report only real problems, ranked by severity.
- For each: file:line, what is wrong, a concrete fix.
- Do not edit files. Do not praise. If nothing is wrong, say so in one line.

Mix models across a team to save cost

A team of subagents doesn't all have to run on the same model. Each agent can use its own, set with the model: line in its file: haiku, sonnet, opus, or inherit to match the main session. Give high-volume, routine work (searching, scanning, summarising) to a small, fast model. Save the strongest model for judgment calls such as planning, debugging and the final review. You get the same result for a fraction of the tokens, and your usage limit lasts longer.

Main session (Opus): plans→3 × Haiku scouts: search in parallel→Sonnet: writes tests→Opus: final review

You can also ask in the prompt: "Use Haiku subagents to scan each module for unused functions, then review their findings yourself."

More agent ideas

AgentToolsModelJob
literature-scoutRead, WebSearchsonnetFind and summarise papers on a question, with citations.
test-writerRead, Write, BashsonnetWrite tests for a given module and run them until green.
debuggerRead, Grep, BashopusReproduce a failure, trace the cause, propose a fix without applying it.
doc-checkerRead, GrephaikuFind places where docs and code disagree.

Writing a good delegation

A subagent cannot see your conversation. A good brief includes the goal, the relevant paths, what "done" looks like, and the format of the answer. Compare:

Weak:    "Look into the login bug."
Strong:  "Find why login returns 401 for valid users. Start in auth/ and
          middleware/. Reproduce with tests/test_login.py. Report the root
          cause with file:line and a proposed fix. Do not edit anything."
Skills vs. subagentsA skill teaches Claude how to do something in the current conversation. A subagent does the work somewhere else and hands back the result. They combine well: a subagent can use a skill.
Trade-offsEach subagent spends its own tokens, so many parallel agents use your usage limit fast. Put routine agents on a cheaper model. Vague briefs produce vague results. For small tasks, doing it directly is cheaper than delegating.
04

Slash commands

Type / in the prompt to see everything available. These ten earn their keep first.

Slash commands control the session itself (context, model, tools) rather than the task. Mastering a handful gives you more leverage than any prompt trick, because most degraded answers come from a cluttered context window, not from a bad question.

A slash command is not a skillYou run a slash command by typing it, and it does one thing right away. Claude never starts it for you. A skill is a playbook that Claude chooses to load when your request matches its description. So /compact manages your session, while a weekly-report skill teaches Claude how to do a task. Both appear in the / menu, but only skills can trigger on their own. Full comparison in section 02 →

No command matches. Try a different word.

  1. /init

    What it does. Analyses your project (languages, build tools, structure) and generates a starter CLAUDE.md.

    How to use. Run it once, at the root of a repo, then edit the result. Run again later to refresh if the project changed a lot.

    > /init
    Best for: the first minute in any repo. Tip: delete lines Claude could infer by reading the code.
  2. /compact

    What it does. Summarises the conversation so far and replaces the long history with that summary. You keep the thread of the work but free most of the context window.

    How to use. Optionally add instructions saying what to preserve.

    > /compact keep the API design decisions and the list of failing tests
    Best for: long sessions, or when answers get slower or forgetful. Compact at natural breakpoints (feature done), not mid-debugging. Claude may also auto-compact when the window fills.
  3. /btw

    What it does. Lets you ask a quick side question without derailing the current task. The answer appears in a temporary overlay and is not added to the conversation history, so it doesn't consume your context or confuse Claude.

    How to use. Type the command with your question, even while Claude is working.

    > /btw what does the --no-verify flag do in git?
    Best for: definitions, syntax reminders, "wait, what does this mean?" moments. Not for questions that should change the plan: ask those normally.
  4. /clear

    What it does. Ends the current conversation context and starts empty. CLAUDE.md and settings still load.

    How to use. Run it whenever you start something unrelated.

    > /clear
    Best for: task switches. Old, irrelevant context actively hurts quality, so clearing is usually better than compacting when the topic changes. Use /resume if you need the old session back.
  5. /resume

    What it does. Shows previous sessions for this project and reopens the one you pick, with its history restored.

    How to use. Run it and choose from the list. From the shell, claude -c continues the most recent session and claude -r opens the picker.

    > /resume
    Best for: picking up yesterday's work, or returning after a /clear.
  6. /rewind

    What it does. Rolls back to an earlier checkpoint: the conversation, Claude's file edits, or both. Pressing Esc twice opens the same menu.

    How to use. Pick the message to return to, then choose what to restore.

    > /rewind
    Best for: Claude went down a wrong path and you want a clean undo. Caveat: it tracks edits made by Claude's file tools, not changes from shell commands or outside edits, so keep using git as your real safety net.
  7. /model

    What it does. Shows and switches the model for the session.

    How to use. Run it and choose, or pass a name.

    > /model
    Best for: using a stronger model for design and hard debugging, and a faster, cheaper one for mechanical edits. Mind your usage limits.
  8. /agents

    What it does. Opens an interface to list, create, edit and delete subagents.

    How to use. Choose "create", scope it (project or personal), describe the role, and pick tools. Claude can draft the prompt for you.

    > /agents
    Best for: building a reviewer, researcher or test writer without hand-writing the file. See section 03.
  9. /mcp

    What it does. Lists configured MCP servers, shows connection status and available tools, and runs the sign-in flow for servers that need OAuth.

    How to use. Run it after adding a server, or whenever a connected tool misbehaves.

    > /mcp
    Best for: debugging "why can't Claude see my GitHub?" See section 05.
  10. /plugin

    What it does. Opens the plugin manager: browse marketplaces, install, enable, disable and update plugins.

    How to use. Add a marketplace, then install from it.

    > /plugin marketplace add owner/repo
> /plugin install name@marketplace
    Best for: adding community skills, agents and commands in one step. See section 06.
Honorable mentions/context shows what is filling your window. /memory edits your CLAUDE.md files. /permissions manages what Claude may run without asking. /help lists everything in your version. Your own commands: save a Markdown prompt in .claude/commands/name.md and run it as /name.
A healthy rhythmStart with /init once. Use /btw for asides, /compact at milestones, /clear between topics, /rewind after wrong turns.
05

MCP

Model Context Protocol is a standard plug that lets Claude use external tools and data.

Out of the box, Claude Code can read files and run shell commands. It cannot see your GitHub issues, query your database, read a Figma file or drive a browser. An MCP server is a small program that exposes such a system as a set of named tools. Claude discovers those tools and calls them like built-ins. One open standard means one server works across many AI apps.

Claude⇄MCP client⇄MCP server⇄GitHub / DB / API

Types of server

Remote (HTTP)

Hosted by a vendor

You give a URL, usually sign in with OAuth. Nothing to install. Typical for Notion, Linear, Figma, GitHub.

Local (stdio)

Runs on your machine

Claude launches a command (via npx, uvx, etc.) and talks to it. Good for local files, local git, databases.

Adding and managing servers

claude mcp add --transport http <name> <url>     # remote server
claude mcp add <name> -- <command> [args]          # local server
claude mcp list                                     # what's configured
claude mcp remove <name>                            # delete one

Scope decides who gets it: --scope local (just you, this project), project (saved in a shared .mcp.json), or user (all your projects). Inside a session, /mcp shows status and handles login.

Git access: three levels

Level 1 · easiest

Plain git through the shell

Claude Code already runs git. No setup needed.

  • "Show what changed on this branch vs main."
  • "Commit these changes with a clear message."
  • "Create a branch for this fix."
Level 2

GitHub CLI (gh)

Install gh and run gh auth login once. Claude can then work with PRs and issues using commands.

  • "Open a PR for this branch."
  • "Summarise comments on PR 42."
Level 3

MCP servers

Structured tools instead of text commands.

  • GitHub MCP: issues, PRs, code search across repos, with token scopes.
  • Git MCP: status, diff, log, commit for one local repo.
# GitHub (remote). Create a fine-grained token first, with only the repos you need.
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer YOUR_GITHUB_TOKEN"

# Local git server for one repo (needs uv installed)
claude mcp add git -- uvx mcp-server-git --repository "C:\path\to\repo"

Try it

> List my open issues labelled "bug", pick the smallest one,
  create a branch, fix it, and open a draft PR that references it.

Which one should I pick?

If you want to…Use
Commit, branch, diff, inspect historyPlain git. No MCP needed.
Create PRs and read comments occasionallygh CLI
Triage issues and search across many reposGitHub MCP
Structured access to one local repo for tools that prefer itGit MCP

Other MCP servers worth knowing

  • Browser automation (Playwright): test and screenshot web apps.
  • Docs lookup (Context7): fetch current library documentation.
  • Design and notes (Figma, Notion): read designs and pages as context.
  • Databases: query read-only replicas to answer data questions.
SafetyNever paste real tokens into files you commit. Grant the minimum scopes, and prefer read-only access first. An MCP server can run code and send data out, so treat it like any software you install: check the publisher and read before trusting. Content fetched by a tool can contain hostile instructions, so stay alert when Claude acts on web pages or issues from strangers. Verify exact URLs and flags against the current official docs, since they change.
Context costEvery connected server adds tool descriptions to the context. Connect only what you need for the current job, and remove the rest.
06

Plugins

A plugin bundles skills, agents, commands, hooks and MCP servers into one installable unit.

Everything in sections 02 to 05 can be created by hand, but sharing it means copying folders around. A plugin packages those pieces with a manifest, and a marketplace (usually just a git repo with an index) lets anyone install it with one command and receive updates. That's how the community distributes workflows.

What can be inside

Skills

Auto-triggered playbooks.

Agents

Ready-made subagents.

Slash commands

New /commands in the menu.

Hooks

Scripts that run on events (before a tool call, on stop).

MCP servers

Connections bundled and pre-configured.

Install workflow

/plugin                                   # open the manager (browse, enable, disable)
/plugin marketplace add <owner/repo>      # register a marketplace
/plugin install <plugin>@<marketplace>    # install
/plugin marketplace update                # pull newer versions
  1. Add the marketplace that hosts the plugin.
  2. Browse in /plugin and open the plugin's page. Read its description and contents.
  3. Install, then restart or reload so skills and commands appear.
  4. Test it on a small task before relying on it.

Community favourites

Minimalism

Ponytail

A "be lazy on purpose" plugin. It nudges Claude to question whether a task needs to exist, prefer the standard library and native platform features over new dependencies, and write one line instead of fifty. It fights the common AI failure mode of over-engineering.

  • Modes: lite, full (default), ultra: how aggressively it cuts.
  • Commands: /ponytail-review reviews a diff for deletable complexity; /ponytail-audit scans a whole repo and ranks what to delete or simplify; /ponytail-debt lists the shortcuts it deliberately left; /ponytail-gain shows measured impact; /ponytail-help is a quick reference.
  • Try it: "Add CSV export" and watch it use the built-in module instead of adding a library.
  • Best when: prototypes, scripts, research code, or any repo that has grown heavy.
Workflow

Superpowers

A widely loved collection of skills that imposes an engineering discipline: clarify the idea first, write a plan, implement with tests first (TDD), review, and verify before claiming done. It makes Claude slower to start typing and much better at finishing correctly.

  • Strength: structured brainstorming and planning that surfaces requirements early.
  • Strength: systematic debugging and verification instead of guess-and-patch.
  • Best when: larger features where a wrong turn is expensive.
Design

Frontend Design

Anthropic's plugin for interface work. It steers Claude away from the generic, template-looking UI toward deliberate typography, color, spacing and layout, and encourages accessible, responsive code.

  • Best when: landing pages, dashboards, prototypes, and tutorials like this one.
  • Pairs with: Ponytail to keep the front-end code small.

How to combine them

A practical stack: Superpowers for process on big tasks, Frontend Design for UI, Ponytail as the counterweight that keeps solutions small. Don't install everything at once. Each plugin adds instructions, and conflicting guidance makes behavior unpredictable.

Trust and verificationPlugins can include hooks and commands that run code on your machine. Install only from sources you trust, read the contents first, and check the publisher and repo in /plugin. Marketplace names and install commands change, so confirm them there instead of copying from old posts. The three above are my picks from community popularity, not an official ranking.
